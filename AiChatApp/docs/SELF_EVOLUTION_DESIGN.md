# Self-Evolution Architecture Design

> Status: Phase 1 (Loop 2) approved for implementation. Loops 3–4 are design-only.
> Author: Hyperion / Claude — 2026-06-11

## 1. Vision

AiChatApp should improve its own behavior from production feedback, without human
prompt-tuning. The system already produces a **fitness signal** — `EvalService`
scores every `AgentStep` on Accuracy / Safety / Format / Helpfulness — but today
that signal is only consumed by skill extraction. This document defines four
evolution loops, ordered by risk, that close the feedback cycle.

| Loop | Target | Mechanism | Status |
|------|--------|-----------|--------|
| 1 | Skills (knowledge of *how*) | Extract reusable skills from high-scoring steps | **Implemented** (`SkillLearningService`) |
| 2 | Prompt templates | Champion/challenger A/B evolution of `pipelines/prompts/*.md` | **This phase** |
| 3 | Pipeline topology | Mutate `stages[]` in `pipelines/*.json` | Designed, not scheduled |
| 4 | Source code | Self-patching via CLI agents on isolated branches | Blocked on test suite |

Common safety invariant for every loop: **each evolution artifact is versioned,
attributable, and automatically reverted when its fitness score regresses.**

## 2. Loop 1 — Skill Auto-Extraction (already implemented)

Flow (existing code, for reference):

1. `AiCollaborationService` fire-and-forgets `EvalService.EvaluateStepAsync` after each step
   (`AiCollaborationService.cs:106,174,327`). Gated by `AiSettings:EvalEnabled`.
2. `EvalService` stores 4 `Evaluation` rows, then triggers
   `SkillLearningService.TryExtractSkillFromStepAsync`.
3. If avg score ≥ 0.8, the LLM decides whether the step contains a reusable strategy and
   creates a `Skill` with `IsAutoGenerated = true, IsApproved = false`.

**Known gaps (follow-ups, not in Phase 1 scope):**
- No UI surface to approve/reject pending auto-generated skills (`IsApproved == false`).
- `SuccessCount`/`UseCount` metrics are recorded but never used for ranking or pruning.

## 3. Loop 2 — Prompt Template Evolution (Phase 1, to implement now)

### 3.1 Concept

Treat each prompt template under `pipelines/prompts/` as a **champion**. A background
service watches aggregated Evaluation scores per template; when a champion underperforms,
the LLM writes a mutated **challenger**. The challenger receives a fraction of live
traffic, accumulates its own scores, and is promoted or rolled back by comparison.
This is a complete evolutionary algorithm (mutation + fitness + selection) that never
touches C# code and is reversible at every step.

### 3.2 New model: `PromptVariant` (`Models/Harness/PromptVariant.cs`)

```csharp
public class PromptVariant
{
    public int Id { get; set; }
    public string TemplatePath { get; set; } = "";   // logical id, e.g. "stage_executor.md"
    public string FileName { get; set; } = "";        // actual file under pipelines/prompts/variants/
    public string Status { get; set; } = "challenger"; // challenger | champion | retired | rolled_back
    public int? ParentVariantId { get; set; }          // null = mutated from the baseline file
    public string Hypothesis { get; set; } = "";       // LLM rationale for the mutation
    public int TrialCount { get; set; }
    public double? AvgScore { get; set; }              // refreshed by the evolution service
    public DateTime CreatedAt { get; set; } = DateTime.UtcNow;
    public DateTime? PromotedAt { get; set; }
}
```

- `DbSet<PromptVariant> PromptVariants` on `AppDbContext`. Table is created by
  `EnsureCreated()` for fresh DBs; for existing DBs add a `CREATE TABLE IF NOT EXISTS`
  block in `ApplicationExtensions.InitializeDatabaseAsync` (same pattern as the existing
  `ALTER TABLE` 补完 logic).
- `AgentStep` gains `public int? PromptVariantId { get; set; }` — add the matching
  `ALTER TABLE AgentSteps ADD COLUMN PromptVariantId INTEGER` in
  `InitializeDatabaseAsync`.

The **baseline file itself** (e.g. `stage_executor.md`) is the implicit champion when no
`PromptVariant` row with `Status == "champion"` exists for that `TemplatePath`.
Variant files live in `pipelines/prompts/variants/` so the originals are never modified —
rollback to baseline is always possible by retiring all variants.

### 3.3 Serving: variant resolution

Add to `PipelineLoaderService` (it already owns `_promptsDir`):

```csharp
public record ResolvedPrompt(string Content, int? VariantId);
public Task<ResolvedPrompt> ResolvePromptAsync(string templatePath, AppDbContext db, Random rng)
```

Resolution rules:
1. Load active champion variant for `templatePath` (or baseline file if none).
2. If an active challenger exists and `rng.NextDouble() < AiSettings:Evolution:ChallengerTraffic`
   (default 0.3), serve the challenger instead and return its `VariantId`.
3. On any error (missing variant file, etc.) fall back to the baseline file and log —
   evolution must never break serving.

Wire-up: the two call sites in `AiCollaborationService`
(`AiCollaborationService.cs:141` and `:218`) switch from `GetPromptTemplateAsync` to
`ResolvePromptAsync` and stamp the returned `VariantId` onto the `AgentStep` being
created, so each Evaluation row is attributable to the exact prompt text that produced it.
`GetPromptTemplateAsync` stays as-is for other callers.

### 3.4 New background service: `PromptEvolutionService` (`Services/Harness/PromptEvolutionService.cs`)

`BackgroundService`, registered next to `ProjectPulseService` in
`ServiceExtensions.cs` (~line 70). Ticks every `AiSettings:Evolution:IntervalMinutes`
(default 30). Entire service is gated by `AiSettings:Evolution:Enabled` (default
**false** — opt-in). Each tick, per distinct `TemplatePath` in use:

**a) Refresh fitness.** For each variant (and the baseline = steps with
`PromptVariantId == null` for that template's stage role), aggregate
`Evaluations.Average(Score)` over the last `WindowHours` (default 72) joined via
`AgentStep.PromptVariantId`. Update `TrialCount` / `AvgScore`.

**b) Mutate.** If there is **no active challenger** for the template AND the current
champion has `TrialCount >= MinSamples` (default 10) AND champion avg <
`TriggerThreshold` (default 0.75): collect the 3 lowest-scoring recent steps
(input / output / eval reasoning), send the current template + failures to
`AiService.ExecuteCliDirectAsync` asking for a rewritten template, validate the result
(non-empty, retains any `{{...}}` placeholders present in the original), write it to
`pipelines/prompts/variants/{templateStem}.v{Id}.md`, insert the `PromptVariant` row.

**c) Select.** If an active challenger has `TrialCount >= MinSamples`:
- challenger avg ≥ champion avg + `MinImprovement` (default 0.02) → promote:
  challenger `Status = "champion"`, `PromotedAt = now`; previous champion → `"retired"`.
- otherwise → `Status = "rolled_back"`. Traffic instantly returns to 100% champion.

**d) Regression guard.** If the current champion is itself an AI-promoted variant and its
rolling avg drops more than `RegressionTolerance` (default 0.05) below the baseline's
historical avg, set it to `"rolled_back"` — serving reverts to the baseline file.

**e) Audit.** Log every mutation/promotion/rollback at `Information` with template path,
scores, and sample counts. (Optional follow-up: push a `ProactiveSuggestion` card via
SignalR on promotion so the admin sees what changed.)

At most **one active challenger per template** at any time — keeps the comparison clean
and bounds LLM cost.

### 3.5 Configuration (`appsettings.json`, under existing `AiSettings`)

```json
"Evolution": {
  "Enabled": false,
  "IntervalMinutes": 30,
  "WindowHours": 72,
  "MinSamples": 10,
  "TriggerThreshold": 0.75,
  "ChallengerTraffic": 0.3,
  "MinImprovement": 0.02,
  "RegressionTolerance": 0.05
}
```

### 3.6 Failure modes & mitigations

| Risk | Mitigation |
|------|-----------|
| LLM returns garbage template | Validation (non-empty, placeholder preservation); on failure skip this tick |
| Variant file deleted on disk | `ResolvePromptAsync` falls back to baseline and logs |
| Eval scores noisy / low volume | `MinSamples` floor; 72h window; `MinImprovement` margin |
| Evolution loop oscillates | One challenger per template; regression guard reverts to immutable baseline |
| SQLite write contention | Service uses its own scope per tick; all writes batched in one `SaveChangesAsync` |

## 4. Loop 3 — Pipeline Topology Evolution (design only)

Same champion/challenger machinery, lifted one level: the mutation target is the
pipeline JSON (`stages[]`) instead of a prompt file.

- Mutations the LLM may propose: insert a validation stage, adjust `maxAttempts`,
  set a stage-specific `provider`, toggle `retryOnQualityFail`.
- Variant pipelines are written as `pipelines/{name}.v{Id}.json` with a distinct
  `name`; `PipelineLoaderService` hot-loads them automatically.
- Fitness = avg of the **final stage** scores plus total latency / retry count
  (topology changes trade quality against cost, so fitness must include cost).
- Reuses `PromptVariant`-style bookkeeping via a `PipelineVariant` table.
- Precondition: Loop 2 running stably for ≥ 2 weeks, since it shares the
  attribution plumbing (`AgentStep` → variant id).

## 5. Loop 4 — Code-Level Self-Modification (design only, gated)

`ExecuteCliAsync` can already run `claude` / `codex` / `opencode` with `workingDir`
pointed at this repository. Turning that into controlled evolution requires hard gates:

1. **Isolation**: agents work only on a dedicated branch/worktree, never the running tree.
2. **Verification**: `dotnet build` + test suite must pass. *The project currently has
   no test suite — building one is the entry criterion for this loop.*
3. **Human approval**: patches surface as `ProactiveSuggestion` cards (SignalR push to
   admin) with diff preview; merge only on explicit approval.
4. **Rollback**: every applied patch maps to a git revision; Eval-score regression after
   deploy triggers an automatic revert suggestion.

## 6. Implementation order

1. **Phase 1 (now)**: §3 in full — model, schema 补完, resolution, background service,

2. Phase 1.5: approval UI for auto-generated skills + promotion notifications.
3. Phase 2: Loop 3 after two weeks of Loop 2 telemetry.
4. Phase 3: test suite, then Loop 4 behind human approval.
